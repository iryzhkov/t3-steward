# Finding packet v1 and review verdict v2

This is the normative contract for units 1.2a and 1.7. It supersedes only the verdict/gate rules named below; [review-verdict/v1](review-verdict-v1.md) retains its document limits, strict JSON parsing, citation/text validation, route/input binding, required-reviewer rules and durable round custody. No implementation, Ruler/grants/security model, tenants or Akasha entry type is defined here.

## 1. Finding packet

Each finding is an object with exactly these required fields (no nulls): `id: string`, `class: string` (enum `defect|regression|safety|note`), `contract_ref: string`, `title: string`, `detail: string`, `affected_paths: string[]`, `failing_tests: string[]`, `reproducer: string`, `severity: string` (enum `high|medium|low`), `blocking: boolean`, `evidence: string[]`, `recommendation: string`. Preserve v1 restrictions on id, severity, title, evidence and recommendation; detail must be nonblank. Paths must be normalized repository-relative paths without traversal; an empty array is allowed for non-file findings. Failing tests name exact tests/commands; reproducer gives executable steps, or is empty when unavailable. Both may be empty only when neither exists.

A valid contract_ref cites the violated exact line of a pinned plan/spec/acceptance document (`relative/path:positive-line`) or an exact test (`test:relative/path:fully-qualified-test-name`). The controller must resolve it against the round's retained contract inputs or reviewed commit and confirm it names an in-scope obligation; syntactic citation alone is insufficient. An absent, empty or invalid reference makes the finding a note, regardless of claimed class. Only contract_ref may be absent on ingestion; normalization materializes it as an empty string and records the original claim and downgrade. Other missing fields are format failures.

Defect violates a stated criterion/invariant/test/clause; regression breaks existing behaviour; safety identifies data loss or a security-relevant failure of the declared operation; note suggests work outside the contract. Safety does not authorize new security work. IDs use v1's pattern, are unique within a reviewer packet and persist for the same obligation and failure across rounds, independent of title, line movement or route changes. The lineage key is (root unit, reviewer slot, id); genuinely new failures get new IDs. The controller retains prior packets and supplies these keys to fresh reviewers; it never silently renames or merges findings.

## 2. Verdict schema and human verdict

`verdict.json` remains one strict JSON object (1 MiB maximum, unknown/duplicate keys forbidden). Its exact required fields are `schema: string` (constant `review-verdict/v2`), `verdict: string` (enum `accept|accept-with-changes|reject`), `inputManifestDigest: string` (64 lowercase hex characters, exact round digest), `reviewerRoute: string` (v1 route rules, exact frozen route), `findings: finding[]` (section 1), `checks_passed: boolean`, `check_evidence: string[]`. Arrays are never null. Check evidence uses v1 citation syntax and points to retained check results. checks_passed is true iff all declared reviewer checks ran and passed; false requires evidence identifying failed or unperformed checks. It is never an evidence list and never substitutes for the independent worker gate. This resolves the boolean/list ambiguity in run-601ead8669deeb9def9b71149b5b4a3e.

After reference normalization, blocking must equal class != note; a contradictory supplied flag is a format failure. Accept has no findings and checks_passed=true; accept-with-changes has one or more notes only and checks_passed=true; reject has at least one blocking finding (including an in-scope failed-check finding when needed). Contradictions are invalid, never acceptance. review.md must be nonempty, at most 1 MiB, with first line exactly `VERDICT: ACCEPT` for either accepting JSON value, or `VERDICT: CHANGES_REQUESTED` for reject. JSON is authoritative; disagreement is a format failure. Markdown lists blocking findings and backlog notes separately using the same IDs.

## 3. Blocking and gate rules

Only validated defect, regression and safety findings count toward the blocking count. Notes never block or enter repair. A required failed/timed-out/invalid/pending reviewer still prevents acceptance; optional lens failures remain visible without gating, as in v1. For this new contract, a completed required accept-with-changes with only notes satisfies the campaign `accept` guard and review gate; retain its original JSON verdict. Reject maps to `changes-requested`. Acceptance also requires the declared worker gate to exit 0 and a fresh review bound to the exact final commit. Collection exit 0 still means valid collection, including reject, not acceptance.

Emit every normalized note as a backlog candidate with project, run/round/reviewer/finding key, title, detail and contract_ref, deduplicated by that source key. Until Akasha exists use `feed post --tag backlog-note --project P`; retain the emission receipt or failure for retry/parent triage. Emission failure does not make a note blocking.

## 4. Unit 1.2a: validation, adjudication and wake

Validate schema, bindings, reference normalization and Markdown agreement before evaluating the gate. Retain raw and normalized packets, diagnostics and check evidence; malformed required results stop as format failures, not repair inputs. `campaign adjudicate --reason` requires a nonblank reason and cited retained evidence. It may correct format without changing meaning, or record a parent's reclassification of identified findings. Retain an append-only event with actor, timestamp, run/round/head/reviewer/id, old/new class, reason and evidence; preserve the original packet and verdict. Reclassification to a blocking class requires a valid contract_ref. An adjudication never changes a substantive reject to acceptance, fabricates passing checks or overrides a failed gate: a reject needing a different substantive verdict requires fresh review. Effective classes change blocking counts and repair selection; a reject with zero remaining blockers stops for fresh review rather than an empty repair.

The wake payload must carry run/task/round IDs, full reviewed head, reviewerRoute, original verdict, effective blocking count, normalized findings and failing_tests (deduplicated union), validation status and adjudication evidence references. Counts and effective classes come from the same retained revision. Bounded wakes must include an explicit truncation marker and a retained packet reference for omitted findings/tests; omission is never an empty packet.

## 5. Unit 1.7: bounded repair

Build repair prompts only from effective blocking findings, with stable IDs, class, contract_ref, detail, paths, tests/reproducer and evidence. Include the instruction “Change nothing for notes”; do not paste note details into the repair prompt. After each repair obtain fresh review at the exact resulting commit. Compare blocking lineage keys and counts with the preceding review: an unchanged key set, or a count that does not strictly shrink, is no progress and stops for parent re-specification, including replacement findings that keep the count level. Phase 1 allows at most two fix rounds (`campaign fix --round-limit 2`), with no automatic third round. Preserve existing lineage custody and exhaustion behaviour; cross-run fix-round counters do not become M16 checkpoint counters.

## 6. Campaign parser field ownership

Lane A1/1.2a adds and owns task `review_output.schema: string` (optional for legacy tasks; new tasks set `review-verdict/v2`), and owns the existing `review_output.verdict`/`verdict_line` selectors and `needs_verdict` acceptance semantics. V2 requires verdict.json and review.md as declared outputs and selects the JSON verdict, never verdict_line fallback. Lane A1/1.7 adds and owns `fix_loops.<name>.no_progress: boolean` (default true for v2 reviews; false refused there), and owns existing `implement`, `review`, `max_rounds` plus the fix lineage round-limit projection; it does not change M16 `review.round_limit` semantics. Existing legacy bounds remain unchanged outside this contract.

Lane A2/1.8 exclusively owns the new campaign-reference variant of `environment.ref: string` (`campaign:<run>/<task>/<name>`) and task `inputs_from_run` with its hash/provenance validation. A1 consumes resolved head/input provenance and does not add or modify those fields. A2 does not edit A1 fields. Existing `inputs_from`, outputs and commits retain their contracts; each lane extends only its named parser/validator cases and fixtures.

## 7. Retention and speed-audit metrics

Retain each packet with root unit, run/task/round, reviewer slot, reviewerRoute, head, raw/effective classes, stable keys, normalization events and adjudication events. For a stated window, per original reviewerRoute, note rate = initially normalized note findings / all findings; reclassification rate = distinct findings whose effective class changed through parent adjudication / all findings. Count each (round, reviewer slot, id) once per denominator, regardless of collection replay or repeated adjudication; attribute changes to the original route, not the adjudicator. Automatic missing-reference downgrades affect note rate, not parent reclassification rate. Report numerator and denominator; zero denominator is “N/A”.

## Compatibility

Historical review-verdict/v1 records remain valid under their original validator and gate semantics, including v1 accept-with-changes behaviour. They are not silently upgraded: v1 lacks contract refs, classes and typed checks, so a new v2 gate/controller refuses them with a schema-migration diagnostic and requests fresh v2 review against the pinned contract and head. Do not infer blocking classes or passing checks from legacy evidence lists or Markdown. This version boundary preserves existing records and prevents a format adjudication from manufacturing substantive acceptance.
